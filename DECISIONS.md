# Nihil — Decision Log

there and are not repeated). New architecture/product decisions are made in the
architecture session (HANDOFF §10) and appended here; implementation-level decisions
that future sessions must know about may also be recorded, marked as such.

| 8 | 2026-06-10 | The WS envelope between daemon and shell is an internal contract living in `@nihil/daemon/contracts`, **not** part of SPEC.md. Envelope payloads that carry protocol concepts MUST use `@nihil/protocol` types directly (`NihilAction`, `ProtocolError`, `ActionMeta`) — never redefine them. SPEC.md §1 scopes transport out explicitly. | Transport evolves with the shell; the protocol governs payload types only. |
| 9 | 2026-06-10 | Sidecar packaging: esbuild single-file bundle with native modules as externals, executed by **system Node ≥ 20** (already a hard product requirement — local-process spawns Node tooling regardless); env doctor validates at shell startup. No SEA/pkg/Bun compile. Revisit a pinned Node sidecar only before public release if support burden demands. | Bundling avoids shipping a runtime; the Node requirement already exists. |
| 10 | 2026-06-10 | `@nihil/protocol` gains a `./schemas` subpath export with `zod` as a **peerDependency**; the main entry stays zero-runtime-deps. Schemas are implemented when the daemon first needs boundary validation (M1 Task 2 acceptable). SPEC.md §9 and the CLAUDE.md invariant reflect this. | Runtime validation at the daemon boundary without polluting the dependency-free core. |
| 11 | 2026-06-10 | Daemon↔shell type sharing via the `@nihil/daemon/contracts` subpath export (type-only consumption by the shell) is approved as an implementation decision. Promote to a `packages/`-level module only if the shell bundler complains. | Avoids premature package proliferation; type-only imports erase at build. |
| 12 | 2026-06-10 | `ExecutionTarget` extended beyond the original §5 sketch to 13 methods: `readFile`, `deleteFile`, `rename`, `copy` (the runner's execute-on-close file verbs; the `<nihil-edit>` apply chain needs current file content) and `listFiles(prefix?)` (recursive, project-relative, excluding node_modules/.git/build artifacts — needed by M2's context-selector and broken-import validator). `docs/technical-spec.md` §5 updated in the same PR. | Without target-level file verbs the runner would bypass the `normalizeProjectPath` funnel and break target portability; extending the interface once is cheaper than twice. |
| 13 | 2026-06-10 | *(implementation-level)* Git transaction division of labor: `target.snapshot()` only returns a ref (`{ kind: "git", ref: <HEAD sha> }`); commit and rollback are executed by the Task 3 runner via the daemon git layer against the shared `projectDir`. This holds for path-sharing targets (local-process, bind-mounted docker); cloud targets (M4) will need a target-side `restore(ref)`. | Keeps the target thin; SPEC §7 already assigns the git transaction to the runner. |
| 14 | 2026-06-10 | `nihil.config.json` is model-writable, which partially bypasses the named-workflows boundary (a `<nihil-write>` can redefine what `<nihil-run workflow="dev">` executes). Task 3's runner MUST treat any write/edit touching `nihil.config.json` as a highlighted action: UI badge + `<nihil-output type="info">` noting the workflow change. Exact mechanism designed during Task 3 planning; no implementation in Task 2. | Closes a quiet hole in the SPEC §4.5 security boundary without forbidding legitimate config evolution. |
| 15 | 2026-06-10 | `ExecutionTarget` gains a 14th method `removePackages(pkgs)` (symmetry with `installPackages`; same per-PM pure command-builder: `pnpm remove` / `npm uninstall`). The Task 3 runner batches `<nihil-add-dependency>` into one install and `<nihil-remove-dependency>` into one remove, ordered **install batch → remove batch**; a package appearing in both yields a warning-level `<nihil-output>` and **remove wins** (deterministic). `technical-spec.md` §5 updated in the same commit. | A SPEC'd tag (`<nihil-remove-dependency>`, §4.4) that silently no-ops erodes the model's trust in the protocol; one interface extension per PR beats two PRs apart. |
| 16 | 2026-06-10 | Runner partial-failure disposition: **rollback only** for user abort, fatal framing errors, and crash recovery. Every other condition commits the actions that succeeded and feeds the failure back via `<nihil-output>` for next-turn self-correction (`STREAM_TRUNCATED`, `EDIT_NO_MATCH`/`EDIT_AMBIGUOUS`, `FILE_NOT_FOUND`, `INSTALL_FAILED`, `WORKFLOW_FAILED`, and **`PLAN_MODE_VIOLATION`** — which is action-level: first-kind-wins means earlier actions were legitimate). Plan-mode is enforced separately by a runner-level `applyEnabled` gate (false → reject any action tag without touching disk; trivial boolean now, full plan flow in M2). | Discarding good edits because test #3 failed would break the `<nihil-output>` feedback loop the protocol is built around. |
| 17 | 2026-06-10 | Crash recovery: the runner writes `.nihil/txn.json` (carrying the snapshot ref) at transaction start and deletes it at successful end/rollback. On reattach with the marker present, the daemon **surfaces it to the user and offers restore-or-keep — never auto-restores**. | A dirty working tree against an uncommitted snapshot is ambiguous; only the user knows whether the half-applied state is worth keeping. |
| 18 | 2026-06-10 | Concurrency: one message in flight per project (serial async queue keyed by `projectId`; different projects run concurrently). Queued messages are **trivially cancellable**; the running message is **abortable only by explicit user action** (→ rollback). No auto-preemption of a running message by a queued one in v1. The deferred longRunning dev server detaches at the tail and does not hold the project lock. | The `snapshot→mutate→commit` transaction is non-reentrant on a shared working tree (`git add -A` is whole-tree); serialization is a correctness requirement, not a UX preference. |
| 19 | 2026-06-10 | Files mutated by a post-commit workflow run (e.g. `lint --fix`) stay **uncommitted and surfaced** to the user in v1 (no dyad-style auto-amend). | The message commit captures the model's authored source; downstream tool mutations are a separate concern the user should see, not silently fold in. |
| 20 | 2026-06-10 | *(implementation-level)* The daemon git layer sits behind a `GitBackend` interface the runner consumes (`snapshot`/`commit`/`rollback`/`restore`). Path-sharing targets (local-process) use a system-git implementation against `projectDir`; M4 cloud targets supply their own backed by a target-side `restore(ref)`. | Lets M4 swap the git mechanism without rewriting the runner. |
| 21 | 2026-06-10 | `ExecutionTarget` gains a 15th method `statFiles(prefix?): Promise<{ path; mtimeMs; size }[]>`. The M1 context selector needs mtime to order files newest-first and size to skip oversized files without reading them. `technical-spec.md` §5 updated in the same docs commit. | The target is the only mtime accessor that stays correct across tiers (local-process via fs.stat; cloud targets provide their own); reading every file just to learn its size would defeat the budget. |
| 22 | 2026-06-11 | Engine interface (M1 Task 4): `Engine.stream(request, { signal }): AsyncIterable<EngineEvent>` with `capabilities.editsViaProtocol` and a thrown `EngineError` taxonomy. M1 ships mode 2 (BYOK, OpenAI-compatible SSE) only — `editsViaProtocol: true`, events `text`/`done`. Mode 1 (ACP, M2) plugs in by adding `file_change`/`tool_call` event variants and `editsViaProtocol: false` without reshaping the mode-2 consumer (open-design under-models this as a boolean; Nihil models file changes as first-class events later). OmniRoute is plain OpenAI-compatible (no special handshake; tier routing is server-side and invisible); base-URL `/v1` is auto-injected only when the configured path has no `/vN` segment. | Designing the event union + capabilities seam now means the M2 vendoring of open-design's runtime does not force a consumer rewrite. |
| 23 | 2026-06-11 | Conversation state in M1 is **in-memory per session** (`Session = { messages, pendingOutput }`); SQLite (technical-spec §8) is deferred. The durable artifact is the git history, and the `Nihil-Message-Id` commit trailer already links commits to messages for a later DB join. | Task 4's goal is the first end-to-end generation; persistence across restarts is a shell/DB concern (M1 Task 6 / M2), not needed to prove the turn loop. |
| 24 | 2026-06-11 | Engine config (validated like Task 1): `NIHIL_ENGINE_BASE_URL` (default `http://localhost:20128`), `NIHIL_ENGINE_API_KEY` (optional — Authorization omitted when absent, for keyless local OmniRoute), `NIHIL_ENGINE_MODEL` (default `"default"`, passed through to OmniRoute), `NIHIL_ENGINE_MAX_TOKENS` (default **16384**, not 8192 — complete-file writes are long by design). On `finishReason === "length"` the turn surfaces a user-visible chat warning; the parser's `STREAM_TRUNCATED` path already protects the transaction (any open tag at EOF is discarded, completed actions commit). Context budget: char/4 token estimate with a **52K effective cap** (char/4 underestimates code ~15%; 60K nominal ceiling), size-skip via statFiles, warning logged when files are excluded. Prompt templates are **embedded** TS constants (bundling-safe) with a doc-sync test against `packages/knowledge/prompts/engine-prompts.md`; `nihil.config.json` workflows gain an optional `description` rendered in `{{WORKFLOWS}}`. | Long outputs must not be truncated by a low cap; the length warning + STREAM_TRUNCATED keep a cut-off response safe; embedded templates survive the esbuild sidecar bundle (DECISIONS #9). |
| 25 | 2026-06-11 | *(threat model)* Prompt injection via project file content is an **accepted, inherent** risk in M1: `{{CONTEXT_FILES}}` embeds raw file contents and `{{WORKFLOWS}}` embeds config command strings into the system prompt, so a malicious file could attempt to steer the model (or spoof a `<nihil-output>`). This is bounded — Nihil is a local, single-tenant tool acting on the user's own machine and git history, every model-provided path still passes `normalizeProjectPath`, `<nihil-run>` is named-workflows-only, and the runner's git transaction makes any bad change reversible. The API key is never placed in the prompt and is redacted (literal value + `redactSecrets`) from any surfaced engine error. M2 may add context provenance/fencing; for M1 the mitigation is the existing execution boundary, not prompt hardening. | The feature requires the model to read and act on file content; no syntactic fence reliably stops injection, and the real safety net is the path funnel + workflow boundary + reversible git transaction, which already hold. |
| 26 | 2026-06-11 | *(found by lane/hardening fuzz review)* `normalizeProjectPath` now rejects NUL and any C0 control character (U+0000–U+001F) appearing in a path attribute, returning `PATH_FORBIDDEN` at the parser boundary. This closes a gap where embedded control bytes — a classic path truncation/injection vector — passed the funnel (the fuzz suite only asserted no-crash on NUL-in-path, not rejection). SPEC §4 gains the one-line rule and `conformance.test.ts` a covering case (conformance 20→21), honoring the same-PR SPEC+conformance invariant. | A path is the one place a control byte is never legitimate; the funnel is the single chokepoint where the protocol can stop it, and doing so is free of false positives (surrounding whitespace is already trimmed before the check). |
